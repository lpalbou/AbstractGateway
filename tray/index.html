    AbstractGateway — Desktop tray icon¶

    abstractgateway serve can show a small icon in the macOS menu bar, the Windows system tray or a Linux panel. It exists so that anyone running a gateway on their own computer — including people who never open a terminal — can see what it is doing and act on it in one click:

    • Open Console — the web console (/console), already signed in: the tray mints a one-time sign-in link locally (the same code as abstractgateway claim; see Security) so an expired browser session never ends on a token prompt. One door: every other console entry point in the menu is a deep link to a tab of it.
    • Apps — the six AbstractFramework apps, one short line each: Open X (running, whoever started it, or installed: started first), Install X… (installs through the gateway, with progress notifications: the same install as the console's Install button, so Code's terminal app comes with it; nothing opens by itself, the menu then offers Open X), Launch Assistant (the desktop app), otherwise the app's name, greyed. See Apps below.
    • Addresses — every address the gateway answers on, each saying where it reaches (http://127.0.0.1:8080 · this computer, http://192.168.1.175:8080 · local network (Wi-Fi), a .local name, a tailscale name, the internet); a click copies it and a notification says what was copied.
    • Conversations — what is going on, by the conversation's title (what you asked, or the automation's name — never a workflow id): Running, Need attention, Scheduled and Recent (the last 24 hours), each row with its own actions. See Conversations below.
    • Pause / Resume AbstractGateway — the one gateway-wide control, under Conversations: stop new steps from running to free the machine or to look at what is going on (the console keeps answering; work queues until you resume). While paused the header reads AbstractGateway — Paused.
    • Models — what is in memory, what can be loaded, and the way to either: eject a loaded model, or preload an installed one. See Models below.
    • Show Activity Window — two live graphs (memory, GPU) and the model list in a small window (needs tkinter; see below).
    • Start AbstractGateway at login — a check item that shows whether this gateway WOULD start at your next login, and switches it. See Start at login.
    • Check for Updates / Restart / Quit / About / Help. About shows the gateway's version, console address and data folder, the AbstractFramework project details (website, source, documentation, where to report an issue or give feedback, contact) and the versions of the framework packages this gateway runs (from GET /api/gateway/about).

    The icon itself is a live gauge: the outer ring fills with system memory in use (blue), the inner ring with GPU load (amber). A green dot in the centre means a workflow step is executing right now; pause bars mean paused; a red ring with ! means the gateway is not answering.

    Everything works offline except Documentation, Report a Problem and Check for Updates, which open a website or check for a newer release (see Restart and update). The documentation is online; the console's docs assistant answers from the llms.txt shipped with the gateway.

    Install¶

    The tray is an optional extra so servers never pull GUI libraries:

    pip install "abstractgateway[tray]"      # pystray + Pillow
    Platform What else is needed Notes
    macOS nothing (pystray installs the pyobjc Cocoa bindings) Retina-crisp icon; native alerts.
    Windows nothing The icon may start in the tray overflow (the ^ chevron); drag it out to pin it.
    Linux the GTK/AppIndicator bindings: sudo apt install python3-gi gir1.2-ayatanaappindicator3-0.1 (Debian/Ubuntu) GNOME needs the AppIndicator and KStatusNotifierItem extension; KDE, XFCE, Cinnamon work out of the box. Pure Wayland sessions without a status-notifier host have no tray.

    The Activity window uses tkinter from the Python standard library. Some Python builds ship without it (Homebrew: brew install python-tk; Debian: sudo apt install python3-tk; pyenv builds need the Tk headers at build time). When it is missing, the item is absent; the console's Resources tab shows the same graphs.

    When the icon appears¶

    At abstractgateway serve time the gateway decides, and says why on stderr:

    While the gateway runs, the icon is there. There is no setting to turn it off and no Hide item in its menu, because the icon is how people who never open a terminal reach their gateway. It is absent only for one of these reasons:

    Situation Outcome
    abstractgateway[tray] not installed not started; the install hint is printed
    No display (SSH session, container, Windows service, macOS daemon, CI) not started (reason headless)
    serve --reload (development) not started (the app runs in uvicorn's reloader child)
    A runner-only process (abstractgateway runner) not started; the tray belongs to the process that serves the console
    serve --no-tray (a test or scratch gateway next to your usual one) not started for this run (reason no_tray_flag)
    A test gateway start: --host 127.0.0.1, a --port other than the configured one (the network setting's, else 8080) and --print-token not started (reason test_gateway), said in one line at start
    Otherwise started; Desktop tray: started (pid …)

    The console's Resources → Gateway card reports which of these applies, as plain text. If the helper itself crashed, POST /api/gateway/host/tray/show (admin) retries it without restarting the gateway.

    Everything the tray shows is also in the console's Resources tab: the Gateway card (pause/resume, update, restart, quit), the memory and GPU meters, and the model table with unload buttons. A paused gateway shows a banner on every console tab with a Resume button.

    Conversations¶

    Conversations ▸ is the machine's work as a person sees it. A row is a conversation — a conversation turn or an automation's occurrence, never a sub-run or an automation's controller — under its title: the automation's name for an occurrence, else the first line of what the person typed (cut at 60 characters), else the workflow's name (GET /host/runs serves it as title with title_source; the Observer's cards use the same text). The list is host-wide, not per-principal: memory, GPU and loaded models on this menu describe the machine, and the conversation list has to describe the same machine. Catalog-published workflows are shown under the name you know them by and are not mistaken for the gateway's own bookkeeping runs. Summoned entities' data planes are not listed (the payload names them in skipped_entity_planes).

    Four sections, each under an information line, nothing hidden without saying so:

    • Running (N) — 🟢 <title> · step 4 · 2m 10s so far, whatever day it started; a run whose sub-run is working counts as running. A row waiting for something that is not a person says what (waiting for a timer, waiting for email.received, waiting for a sub-run) and stays here. A paused conversation reads ⏸ <title> · paused. The submenu: when it started, Open in Observer, Pause (the conversation stops at its next step; POST /commands type pause, the whole run tree) or Resume (type resume), and Stop… (asks first; type cancel, with the reason "Stopped from the AbstractGateway menu"). Running — none when nothing runs.
    • Need attention (N) — only an approval or a question, the two waits a person must act on. 🟡 <title> · approve \execute_command`: the submenu shows what is asked on one line, then **Show and approve…** — a dialog with the tool name and its arguments in full (pretty JSON, cut at about 1500 characters with "open in Observer for the rest"), buttons **Approve** / **Deny** / **Cancel**, Cancel being the default and what Esc does — and **Deny** from the row. An approval is never sent from a bare menu click. The answer is the sameresumecommand the Assistant and Code send:{wait_key, payload: {"approved": true|false}}on the run that holds the wait (a sub-run's approval belongs to its parent's row; the dialog reads the full arguments fromGET /host/runs/{run_id}/wait).🟡 · a question`: the question, one line; free-text answers stay in the clients (the Assistant, Code, the console).</li> <li><strong>Scheduled (N)</strong> — the automations (<code>GET /automations</code>), active and paused: <code>⏱ <automation title> · Every day at 09:00 · next Fri 17 Oct 09:00</code>, <code>⏱ <title> · When Python news has a new item</code> — the trigger in the gateway's words (<code>trigger_text</code>, with the next run from <code>schedule_text</code> for a schedule); the tray computes no next run. The submenu: <strong>Open in Observer</strong> (the Automations page), <strong>Run now</strong>, <strong>Pause</strong> / <strong>Resume</strong> (<code>POST /automations/{id}/commands</code>, types <code>automation.run_now</code>, <code>automation.pause</code>, <code>automation.resume</code>), each offered only when the automation's <code>capabilities</code> list it; the gateway's refusal (an occurrence already running, an archived automation) is shown with its words.</li> <li><strong>Recent — 4 done · 1 cancelled</strong> — the conversations that finished in the last 24 hours (✅ completed, ❌ failed, ⚪️ cancelled), newest first, with the step count and how long each took; five rows, then <code>…and N more</code>. The submenu: when it started, <strong>Open in Observer</strong>.</li> </ul> <p><strong>Open in Observer</strong> opens that conversation's page (or the Automations page) signed in; a stopped Observer the gateway manages is started first; greyed when Observer is not installed. <strong>Open Conversations in Console</strong> at the bottom is the full list.</p> <p>Another account's conversation (the gateway runs several accounts) is listed — the machine is busy with it — but its Pause, Stop and approval controls are greyed and the row says <code>Another account's conversation — act on it from its own app</code>: the tray's commands reach the plane of its own identity (the payload's <code>caller_plane</code>), never another account's runs.</p> <p>The conversation rows are read every 20 seconds (<code>GET /host/runs</code>, cached a few seconds on the gateway; one run document per row) and right after each action. A duration that ticks never rebuilds the menu under the cursor. The <strong>Scheduled</strong> rows follow your event stream instead (below): they are read again when an automation event arrives, after each action, and every 5 minutes to catch an automation created or renamed elsewhere; on a gateway without the event stream they keep the 20-second read.</p> <h2 id="automation-notifications">Automation notifications<a class="headerlink" href="#automation-notifications" title="Permanent link">¶</a></h2> <p>The tray follows your event stream (<code>GET /api/gateway/me/events/stream</code>, <a href="../api/#your-event-stream-apigatewaymeevents">api.md</a>): it reads what happened before it started, then stays connected and picks up where it left off after a break (<code>Last-Event-ID</code>), so nothing is missed and nothing is shown twice.</p> <ul> <li><strong>A notification per automation item.</strong> When an automation has something for you (its run asked to notify, or it failed after its retries), the tray shows one notification: <code><automation title></code> · <em><automation title> has a new result — open it in the Assistant.</em>, or <code><automation title> failed</code> · <em><automation title> failed after its retries — see Automations in the Assistant.</em> Items that existed before the tray started are not shown again.</li> <li><strong>A notification per wait on you.</strong> A conversation that stops for your approval (<em>Approval needed</em> · <em>A conversation waits for your approval — open the Assistant.</em>) or your answer (<em>A question for you</em>) is announced once. The same switch from a terminal:</p> <div class="highlight"><pre><span></span><code>abstractgateway<span class="w"> </span>service<span class="w"> </span>status<span class="w"> </span><span class="c1"># on | off | broken | other, and why</span> abstractgateway<span class="w"> </span>service<span class="w"> </span><span class="nb">enable</span><span class="w"> </span><span class="c1"># this gateway at next login; the Network setting binds it</span> abstractgateway<span class="w"> </span>service<span class="w"> </span>disable<span class="w"> </span><span class="c1"># the running gateway keeps running</span> abstractgateway<span class="w"> </span>service<span class="w"> </span>install<span class="w"> </span><span class="c1"># enable + start now + wait for health (installers)</span> abstractgateway<span class="w"> </span>service<span class="w"> </span>uninstall<span class="w"> </span><span class="c1"># disable + stop it</span> </code></pre></div> <h2 id="network-and-addresses">Network and addresses<a class="headerlink" href="#network-and-addresses" title="Permanent link">¶</a></h2> <p><strong>Addresses ▸</strong> lists every address the gateway answers on (loopback, each network interface, the machine's <code>.local</code> name, a tailscale name, a public one) with where it reaches — <code>http://192.168.1.23:8080 · local network (Wi-Fi)</code> — and copies the one you click. <strong>Network ▸</strong> shows what runs now (<code>Now: local network · 0.0.0.0:8080</code>) and three choices — <strong>Localhost only</strong>, <strong>Local network</strong>, <strong>Internet…</strong> — whose mark is what is <em>set</em>. Choosing one saves it (<code>POST /api/gateway/network</code>); when it needs a restart, <strong>Restart to apply</strong> appears (and the Network item says <em>restart required</em>). <strong>Internet…</strong> first shows what exposing the gateway means, with the gateway's own warnings, and posts only after you acknowledge it. A refusal (for example sign-in not set up for that mode) opens a dialog with the reason and the fix.</p> <p>A gateway without the network settings route says so in the Network submenu, and Addresses still offers the address the tray talks to.</p> <h2 id="menus-without-submenus">Menus without submenus<a class="headerlink" href="#menus-without-submenus" title="Permanent link">¶</a></h2> <p>pystray draws submenus and check marks on macOS, Windows and Linux (AppIndicator). Some Linux panels drop submenus: set <code>"flat_menu": true</code> in <code><data_dir>/tray/prefs.json</code> and restart the gateway — every row is kept, prefixed with its path (<code>Models › Load a Model › MLX › …</code>). pystray's plain X11 backend (<code>xorg</code>) has no menu at all: clicking the icon opens the console, and a notification at start names the CLI equivalents (<code>abstractgateway service …</code>, <code>apps …</code>, <code>models …</code>).</p> <h2 id="pause">Pause<a class="headerlink" href="#pause" title="Permanent link">¶</a></h2> <p><strong>⏸ Pause AbstractGateway</strong> (under Conversations) is process-wide and <strong>persists across restarts</strong>: a laptop paused to get its GPU back does not silently resume after a reboot or an update. One conversation is paused from its own row instead (see <em>Conversations</em>). While the gateway is paused:</p> <ul> <li>no new workflow step starts — runs, schedules and bridge-started work are accepted and wait;</li> <li>a step already inside an LLM or tool call finishes first (the menu says "Finishing N runs at the next step");</li> <li>the console, the API and connected apps keep answering; cancelling a run still works;</li> <li>summoned entities' own-time loops are <strong>not</strong> affected (they are separate processes with their own lifecycle controls);</li> <li><code>GET /api/health</code> carries <code>"paused": true</code> while <code>status</code> stays <code>"healthy"</code> — a supervisor must never recycle a paused gateway.</li> </ul> <p>Pause reaches inside a tick: AbstractRuntime's <code>Runtime.tick(step_gate=…)</code> consults the gateway's gate at every step boundary. Where the runtime does not offer that gate, the pause takes effect at tick boundaries (up to <code>tick_max_steps</code> steps later); <code>GET /host/runner</code> reports <code>step_gate_supported</code> and the menu says so.</p> <p>In the split layout (<code>serve --no-runner</code> + <code>abstractgateway runner</code>) the pause is written to <code><data_dir>/gateway_paused.json</code> and the runner process picks it up within about two seconds.</p> <h2 id="restart-and-update">Restart and update<a class="headerlink" href="#restart-and-update" title="Permanent link">¶</a></h2> <p><strong>Restart</strong> asks uvicorn for its normal graceful shutdown (runner drain, entity close), then relaunches the same command in the same environment (<code>python -m abstractgateway …</code>). On macOS and Linux the process keeps its PID and terminal; on Windows a new process is spawned on the same console. Restart is refused (HTTP 409, greyed out in the tray) under <code>serve --reload</code>, when the server was not started by <code>abstractgateway serve</code>, or while an update is being installed.</p> <p><strong>Check for Updates</strong> (the tray), <strong>Check now</strong> (web console, <strong>Resources > Gateway > Version</strong>) and <code>u</code> in the terminal console's <strong>F3</strong> panel all ask the gateway the same question and show its answer word for word: the version line, a hint, and <strong>Update to …</strong> with a confirmation that says exactly what runs. The check takes at most a few seconds, runs at most once per hour unless you ask again, and offline is a normal answer, not an error. Updating is for admins.</p> <p>What the check compares and what <strong>Update</strong> runs depends on how the gateway was installed:</p> <table> <thead> <tr> <th>Install</th> <th>Compared with</th> <p>The gateway recognises an installer install by the installer's record in its data folder (<code>bootstrap.env</code>), which also names the AbstractFramework release installed. <strong>Update</strong> then runs the same installer as the one-line install, so updating from the tray, either console or by running the line again in a terminal does the same thing:</p> <ul> <li><strong>The release.</strong> The check reads the AbstractFramework repository's <code>main</code> branch at one commit: its install manifest (<code>docs/installers/install-manifest.json</code>, the release version and the gateway version it pins) and its <code>scripts/install.sh</code>. The line reads <code>AbstractFramework 0.6.1 · gateway 0.7.1 · AbstractFramework 0.6.2 available</code>. An install made with <code>--pin</code> records no release; it is offered the release only when the release's gateway is newer than the one installed.</li> <li><strong>What runs.</strong> The confirmation names the script's address (<code>https://abstractframework.ai/install.sh</code>), the commit and the script's sha256, and the command: <code>/bin/sh install.sh --yes --no-start --no-open --no-modify-path --data-dir <data folder></code>. The gateway runs exactly the file it checked, written to a new file of its own for that run; the start must name the sha256 the confirmation showed, and if a newer check fetched a different script in between, <strong>Update</strong> refuses and asks you to check again. One update runs at a time.</li> <li><strong>How it runs.</strong> Nothing is asked and nothing is opened. Start at login stays as it is. The installer keeps your profile, port and the choices it remembers, moves every package to the release's tested versions, and does not stop the running gateway. Its output is the update log (console: <strong>Update log</strong> under the version line; the tray shows its last lines if it fails). The installer's own log is the newest <code>install-*.log</code> in <code><data folder>/logs/</code>.</li> <li><strong>The result.</strong> What moved (<code>AbstractFramework 0.6.1 -> 0.6.2, abstractgateway 0.7.1 -> 0.7.2, …</code>) and <strong>Restart</strong> to finish; <strong>Already up to date</strong> when the installer changed nothing (no restart is offered); or the installer's exit code with the last lines of its log. The running gateway keeps working in every case.</li> <li><strong>Windows</strong> keeps a running program's files locked, so the gateway cannot update itself in place. The hint shows the line to paste in PowerShell; the installer stops the gateway, updates everything and starts it again:</li> </ul> <div class="highlight"><pre><span></span><code><span class="n">powershell</span> <span class="n">-ExecutionPolicy</span> <span class="n">ByPass</span> <span class="n">-c</span> <span class="s2">"irm https://raw.githubusercontent.com/lpalbou/AbstractFramework/main/scripts/install.ps1 | iex"</span> </code></pre></div> <h3 id="from-a-terminal-abstractgateway-update">From a terminal: <code>abstractgateway update</code><a class="headerlink" href="#from-a-terminal-abstractgateway-update" title="Permanent link">¶</a></h3> <p>The same update as a shell command, for an installer install (macOS, Linux; the one-line install or the double-click installer):</p> <div class="highlight"><pre><span></span><code>abstractgateway<span class="w"> </span>update<span class="w"> </span>--check<span class="w"> </span><span class="c1"># what would change; exit 0 up to date, 10 when an update exists</span> abstractgateway<span class="w"> </span>update<span class="w"> </span><span class="c1"># show it, ask once, run the installer here</span> abstractgateway<span class="w"> </span>update<span class="w"> </span>--yes<span class="w"> </span><span class="c1"># ask nothing (scripts, no terminal)</span> abstractgateway<span class="w"> </span>--update<span class="w"> </span><span class="c1"># the same command</span> </code></pre></div> <p>It prints the installed and the newest release, then <strong>What changes</strong>: every package whose installed version differs from the release's (the framework, the gateway, the other Python packages of the gateway's environment, the browser apps and the terminal apps, each as <code>installed -> new</code>), then <strong>Release notes</strong>: the AbstractFramework changelog sections between the two releases, newest first (when the changelog cannot be fetched it says so and goes on). <code>--check</code> stops there. Otherwise it asks <code>Upgrade now? [Y/n]</code> and runs the sha-checked installer in the foreground, its output on your terminal: <code>/bin/sh <data folder>/update/install-….sh --yes --no-open --no-modify-path --data-dir <data folder></code>. No <code>--no-start</code> here: the command is not the gateway process, so the installer keeps your port, profile and login choices and restarts the gateway service itself. The command exits with the installer's exit code and ends with the console's address. On Windows it starts the PowerShell installer in a new window and exits at once (the running command would otherwise hold files the installer replaces). An install the installer did not make (a source checkout, a container, a plain pip / uv / pipx install) is refused with the command to run instead.</p> <p>The newest gateway outside a release is a command-line choice: run the installer with <code>--pin latest</code> (see the AbstractFramework install guide).</p> <h3 id="other-installs">Other installs<a class="headerlink" href="#other-installs" title="Permanent link">¶</a></h3> <p>The installed extras (<code>apple</code>, <code>gpu</code>, <code>embeddings</code>) are detected and kept. The upgrade runs in the background (its log is under the console's version line); <strong>Already up to date</strong> is reported when the package manager installed nothing newer.</p> <p>In every case the running process keeps serving the old code until it restarts: the tray offers <strong>Restart Now</strong>, the console's Gateway card <strong>Restart gateway…</strong>.</p> <h2 id="security">Security<a class="headerlink" href="#security" title="Permanent link">¶</a></h2> <p>The tray talks to the gateway over loopback HTTP with a <strong>per-process ephemeral admin token</strong> handed over on the helper's stdin — never on the command line, never in the environment, never on disk. The token is accepted only from a loopback socket peer (<code>127.0.0.0/8</code>, <code>::1</code>) and dies with the process. Audit-log entries made through it carry <code>source: loopback-ephemeral:desktop-tray</code>.</p> <p><strong>Signed-in links.</strong> <em>Open Console</em> does not ask the gateway to sign anyone in — there is no such endpoint, by design. The tray writes a one-time claim code under <code><data_dir>/auth/claims/</code> (only someone who can write the data folder can), valid 2 minutes, and opens <code>/console#claim=<code></code>; the console redeems it once, from a loopback browser only. A gateway running with a static token (no user accounts) cannot redeem claims, so the plain URL opens and a notification says why. <em>Copy Console Link</em> copies the plain URL: a sign-in link does not belong on a clipboard. App links use the gateway's one-time handover (<code>POST /api/gateway/apps/{id}/open</code>, 2 minutes, single use).</p> <p><code>FORWARDED_ALLOW_IPS=*</code> (uvicorn's proxy setting) would let any client rewrite its peer address; the gateway warns at boot when it sees that with a tray running. Use a concrete proxy IP.</p> <h2 id="troubleshooting">Troubleshooting<a class="headerlink" href="#troubleshooting" title="Permanent link">¶</a></h2> <p>See <a href="../troubleshooting/#there-is-no-tray-icon">troubleshooting.md</a> for a missing icon. Other cases:</p> <ul> <li><strong>The helper starts then disappears</strong>: read <code><data_dir>/logs/tray.log</code>; <code>GET /api/gateway/host/tray</code> reports <code>exit_code</code> and the readiness failure. After two crashes in a row it is not restarted automatically; <code>POST /api/gateway/host/tray/show</code> (admin) starts it again.</li> <li><strong>The icon says "Not responding"</strong>: the gateway is restarting, stopped or unresponsive. <em>Force Quit</em> in that state sends the gateway process SIGTERM and, after five seconds, kills it.</li> </ul> <h2 id="licensing-note">Licensing note<a class="headerlink" href="#licensing-note" title="Permanent link">¶</a></h2> <p><code>pystray</code> is LGPL-3.0 and <code>python-xlib</code> (Linux) is LGPL-2.1.
