    Summoned entities¶

    The gateway owns the lifecycle of summoned entities — persistent identities (like "Orion") that live across sessions, users, and workplaces; each summon is a re-adoption of the same self. An entity is not a chatbot configuration: it is a home directory holding everything the entity is and has lived, plus the lifecycle surface to create, inspect, verify, and summon it.

    This page uses human words first, API names in parentheses.

    Who can see an entity: an admin sees every entity; anyone else sees only the entities they created (recorded as created_by when the entity is created). An entity you may not see answers like a missing one (404). An entity is a member account (the two roles are admin and member).

    Who configures an entity: its creator — mind, voice, tools per phase, instructions, skills, workspaces, preferences, archive, unarchive and its Active switch — within what the admin authorised (the models and voices the gateway offers, the workspace caps, no tier-2 tool); an admin always can. Another member gets "Only an admin or 's creator can …", and the entity never changes its own settings. Sleep and wake, personal time, the work order, memory review and the memory index rebuild stay an admin's. GET /api/gateway/entities/{name}/access says what you may change. See security.md.

    In the consoles, entities are rows of the Accounts table, with an Active switch that suspends and resumes them; they have no token to rotate and no delete. See security.md and console.md.

    What an entity is¶

    A summoned entity lives in two files at its home:

    • Its memory (memory.sqlite3) — the involuntary record: everything that happens to it, its standing feelings about anything it has experienced (people, tools, ideas, places, even a time of day), and its always-on identity core planted from a spark document. Things happen to you and you are forced to remember; that is what forges who you are.
    • Its diary — "the book" (home.sqlite3) — the voluntary record: what the entity elects to write. First-person, hash-chained, written only by the entity itself, and never deletable — there is no delete surface anywhere in the code, on disk, in the CLI, or over HTTP.

    Next to those live the attested seed (spark.yaml, stored byte-verbatim at creation — the spark is engrammed once and kept for life) and the gateway's manifest.json (an internal record: the engraved owner key — entity:<name>, or entity:<name>@<home-id> on homes created with that form, kept for life because journals are append-only — plus creation time, the spark hash, and reserved fields for the future key/signature work).

    The entity's ID — the handle — is <name>@<gateway ip>, e.g. orion@192.168.1.146: the name at its home gateway's current LAN address (or the operator-declared ABSTRACTGATEWAY_DECLARED_ADDRESS). That is what every operator surface shows as "Entity ID". The manifest string above is a birth marker, never the id; the address is never written at rest, so moving the gateway never touches a record.

    Copying the home directory moves the entity. The home_id in the manifest names the birth home and is kept on copy; re-homing is deferred to the keys work.

    Lifecycle surface¶

    CLI (there is deliberately no delete verb):

    abstractgateway entity create --name Orion [--spark spark.yaml] [--data-dir ./runtime]
abstractgateway entity list
abstractgateway entity inspect Orion      # who it is, what it wrote, how it feels
abstractgateway entity card Orion         # the identity card: a page to know your companion
abstractgateway entity verify Orion       # both attestation chains + the spark hash

    Through the running gateway's routes (--url, else the gateway running for this data dir; --token, else $ABSTRACTGATEWAY_AUTH_TOKEN, else this data dir's bootstrap admin token for a loopback URL; --json prints the route's payload; a refusal prints the gateway's sentence and exits 2):

    abstractgateway entity identity get Orion [--rev N]     # its look, voice, reference, fingerprint, age
abstractgateway entity identity set Orion --style watch-well --color "#3366cc" \
    --provider kokoro --model kokoro-82m --voice am_adam [--speed 1.1] [--quality-preset P]
abstractgateway entity record Orion [--track-record | --reputation | --acquaintances] [--since ISO]

    entity record prints "No experience yet" where nothing was counted, and says what the numbers mean: success is the work finishing (completion rate only); how good it was is not assessed yet.

    HTTP (rides the same auth as every /api/gateway/* endpoint):

    Method Path What it does
    POST /api/gateway/entities Create: lint the spark, store it verbatim, plant the identity core (engram), write the manifest. Idempotent for the same spark; a changed document is refused (409) — identity does not silently drift.
    GET /api/gateway/entities List homes.
    GET /api/gateway/entities/{name} Inspect: the folded identity core, recent diary gists, top standings, and the wake reasons — open questions (curiosity), open problems (something wrong), incubating ideas (direction). Pure reads — inspecting never counts as the entity using its memory.
    GET /api/gateway/entities/{name}/card The identity card ("something to know our companion"): the engine compositor's sections — identity, age+context, current state (a window, never a point), likes/dislikes (G+ and G− separate; ambivalence preserved), open/resolved questions (resolution is the entity's own act), key moments, discoveries — each with provenance, plus gateway overlays (name/age, operator state, mind substrate, host moments). ?as_of=<seq> anchors the card at a journal moment ("who was he at seq 500"). Interest, lesson and key-moment briefs carry their stored understanding. Pure reads.
    GET /api/gateway/entities/{name}/tile What one small card about an entity shows, and nothing more (about 2 KB instead of up to 90 KB): name, look, age, mind (its model); what it is doing now (now.phase: visit, work, personal, sleep, idle or stopped; now.state, the operator state under it; busy; since; trouble: {kind: "own_time_failed"} when its own time stopped after repeated failures); its newest interests (into_lately), its newest open problem or question (on_its_mind), its latest lesson, its last meaningful moment (last_moment.kind from a closed set: summon, session_closed, sleep, wake, pause, personal_started, personal_stop_requested, personal_frozen, phase_changed, substrate_changed, night_voice, work_order_changed, task_inbox_changed, identity_changed) and counts. The roster (GET /entities) advertises it as reads.tile; a client that does not find it there reads the card. Pure read; a source that cannot be read costs its facts with a labelled warning, never the tile; a held home answers 409.
    GET /api/gateway/entities/{name}/verify Verify the book's hash chain, the graph projections against the book, the spark document against the engrammed marker, and the manifest.
    POST /api/gateway/entities/{name}/summon Summon the entity into a work session (below).
    POST /api/gateway/entities/{name}/chat/open Open a hosted conversation (the web chat backend; same turn loop as entity chat). Auto-yields the entity's own-time loop like --pause-loop; one live session per home; a refused prelude aborts verbatim. The gateway never caps the entity's output: the model works at its full capacity (the former max_output_tokens field is ignored and the response then carries a one-line deprecation).
    POST /api/gateway/entities/{name}/chat/{chat_id}/turn One honest turn. tools_ran in the response is driver-authored data — what actually executed, never derived from the reply prose.
    POST /api/gateway/entities/{name}/chat/{chat_id}/close End the visit: reflection pass (feelings move there), close summary, the own-time loop woken if the open yielded it.
    GET /api/gateway/entities/{name}/chat Is a visit open on this home right now? (one life, one summon)
    GET /api/gateway/entities/{name}/replay The observable life as a bounded stream (NDJSON): every memory-journal moment (formations, recalls, feelings, belief changes) plus gateway host markers (summons, refused preludes), in one strict sequence.
    GET /api/gateway/entities/{name}/replay/stream The same stream as a live tail (SSE; Last-Event-ID resumes exactly). History scrub and realtime are one format — a viewer that renders one renders both.
    GET /api/gateway/entities/{name}/track-record, /reputation, /acquaintances What it has done (runs, successes, failures, tokens, per kind of task), how far it can be trusted per kind of task (with how many outcomes that rests on), and the entities and humans it met. Derived from its home's records; nothing is stored. See API: track record, reputation and acquaintances.

    Phases, toggles and the kill switch¶

    An entity is in exactly one of four activity phases: visit (a person is talking with it), work (an automation, an agent's request or its work order), personal (its own time) or sleep (maintenance). Two statuses sit outside the four phases: - idle: awake and reachable, with nothing of its own running; - stopped: the kill switch.

    personal is the one toggle: a permission, not an order. Own time is yours to give and to take back. Turning personal on starts it; neither the gateway nor the entity ever grants it. There is no work switch: work starts when a job is queued (a work order, a task you leave him, a request or an automation that reaches him), whether or not own time is given. A job during own time interrupts it; when all his jobs are done he goes back to his own time if it is still given, else he is idle.

    When something interrupts own time (a visit, a sleep, a request), the gateway brings the entity back to it afterwards, as long as personal is still on. Stop is different: it takes own time back. It never starts own time for an entity that was not in it, and never under a visit, a sleep, work or the kill switch. If own time stops unexpectedly, the phase is idle with a blocked reason and a retry action; nothing restarts it behind your back. When own time ends because it was asked to (personal or work turned off, a removed step, or nothing of its own left to return to), that is not a crash: the entity is awake and reachable, idle, with no blocked reason. Sleep is entered only by the operator's sleep, by the entity's own decision, or, while it is idle, once its Mind's sleep thresholds are reached (sleep.after_hours since its last completed sleep, or sleep.after_events new memories since it; the gateway checks every few minutes and puts one entity to sleep at a time). Such a sleep is its own (sleep.kind self, its reason names the threshold); when its maintenance is done it is idle again. The entity's own sleep has no set time: its sleep.ends is "when maintenance is done". A sleep is never followed by another sleep.

    Method Path What it does
    GET /api/gateway/entities/{name}/life_state The phase bar's one read. phase (visit, work, personal, sleep, idle or stopped), toggles {personal}, stopped, since (when this phase began), sentence (one plain line, no clock time), next, blocked {code, sentence, action}, can {visit, sleep_now, toggle_personal} (each {allowed, sentence}), the visit and sleep details, work {jobs_queued, current} (current is the job running now: {kind, run_id, since}, kind one of summon, automation, work_order, task), and rev. rev goes up whenever anything in the answer changes and never goes down, even across restarts. Every field is always present; null when it does not apply.
    PUT /api/gateway/entities/{name}/life_state/toggles {personal: bool} (admin). Personal off is idle at once: the turn in flight finishes (sentence: "Own time withdrawn: he finishes what he is doing, then goes idle."), nothing after it runs, and the entity is never put to sleep. A body with work is refused (422 unknown_field, "There is no work switch: work starts when a job is queued.").
    POST /api/gateway/entities/{name}/lifecycle {action: "stop" \| "resume" \| "retry"} (admin). stop is instant and unconditional: everything stops, open visits close, live runs are cancelled, the own-time process is killed, and own time is revoked (personal turns off; when it was on, the answer's own_time_revoked is true and its items carry {item: "own_time", code: "revoked", outcome: "done", sentence: "Own time was revoked."}). The answer lists each item with its outcome; press it again to retry anything left over. When the own-time process could not be stopped, its row says why. resume wakes the entity (never into a sleep) and it is idle: nothing from before the Stop comes back, and own time only when you turn personal on again. retry restarts own time after a crash.

    A visit never fails, in every phase and every sleep: the door opens at once and the entity joins as soon as it finishes the step in progress or its maintenance pass. While a visit lasts the phase is visit. When it closes, the entity returns to what it was doing: an interrupted sleep continues as the same sleep, and own time resumes if it was running and its toggle is still on. Stopped is the one exception: the visit door answers 409 stopped_use_resume "Stopped. Resume to visit."

    Every change reaches open clients on the entity's replay stream (GET .../replay/stream) as a host envelope with payload.kind: "phase_changed": {name, from, to, phase, toggles, stopped, since, rev, cause, sentence}. Keep the highest rev and re-read life_state for the details. Changes made inside the own-time loop arrive the same way.

    The older routes keep working and name their successor (Deprecation: true and a Link header): - POST .../state {state: "paused"} and POST .../loop/stop {mode: "freeze"} are the kill switch; - restore (or awake while stopped) is resume; - POST .../loop/start and PUT .../personal-grant turn personal on (loop/start remembers its parameters, and is deferred, never refused, while a visit, work or a sleep holds the phase); - a graceful POST .../loop/stop turns personal off.

    POST .../state {state: "sleep"} is the operator's sleep. With dream: true the maintenance pass runs and the entity wakes when it is done. The sleep no longer turns personal off or clears the work order. It is refused during a visit (in_visit) and right after a sleep (already_asleep).

    Status code When
    409 stopped_use_resume Stopped: resume first
    409 in_visit The operator sleep while a visit is open (a visit is never ended implicitly)
    409 already_asleep The operator sleep right after (or during) a sleep
    422 invalid_body, invalid_toggles, unknown_field, invalid_action The request body
    404 entity_not_found No such entity (life_state: null)

    These refusals carry {code, detail: {reason_code, message, life_state}} and the X-Gateway-Error-Code header.

    The entity's mind and voice¶

    Method Path What it does
    GET /api/gateway/entities/{name}/substrate Its mind: its own choice (provider, model, thinking, speculation; null when it has none), gateway_default (the gateway's text route), effective (what its next visit thinks with) and source: entity, gateway, or unset (the gateway has no text model; note says what to do).
    GET /api/gateway/entities/{name}/access May you change its settings? {entity, can_configure, as: "admin" \| "creator" \| null, reason, admin_only_tools: {tools, reason}, admin_only: {available, reason}} — reason is the sentence to show on a control you can't use.
    PUT /api/gateway/entities/{name}/substrate An admin or its creator (the creator: a model the gateway offers, else 403 not_offered naming the offered models). {provider, model, thinking?, speculation?} sets its own mind; {"clear": true} returns it to the gateway default. Each change is recorded in its history (substrate_changed). speculation is MTP: false (off) or {"mode": "native_mtp", "num_draft_tokens": N}.
    GET /api/gateway/entities/{name}/cognition-profile What each part of its thinking uses, and its memory settings (below). capabilities.{summaries,understanding,extraction}: {choice, effective, source}, where choice is {"inherit": "mind"} or {provider, model, thinking, max_input_tokens}, effective is {provider, model, thinking} (null only when it inherits and the gateway has no text model) and source is profile or mind; recall: {shelf_size, source, applies_to_running_loop: "on restart"}; rebuild: {sensitivity, cap_per_turn, source, sources} (source per block, sources per field: profile or default); lookback: {context, source}; mind: {provider, model, thinking, source} (entity, gateway, or unset with a note).
    PUT /api/gateway/entities/{name}/cognition-profile An admin or its creator (the creator: a changed capability must use a model the gateway offers, else 403 not_offered). Any subset of {capabilities: {cap: {"inherit": "mind"} \| {provider, model, thinking?, max_input_tokens?} \| null}, recall: {shelf_size: int \| null}, rebuild: {sensitivity: number \| null, cap_per_turn: int \| null}, lookback: {context: "day" \| "tick" \| null}}: what is absent keeps its value, null returns it to its default. Refused with a sentence (400) outside the ranges below, for an unknown field, or for an endpoint: provider that is not an enabled connection. Each change is recorded in its history (cognition_profile_changed, old and new) before the file changes; the answer is the GET shape.
    GET /api/gateway/entities/{name}/identity[?rev=N] Its digital identity (framework ADR 0052): {entity_id, identity: {rev, avatar: {style, style_requested, color, source, watch_code}, voice, set_at, set_by}, identity_ref, fingerprint, age: {born, days}}. avatar.style is the design drawn and style_requested the id the record holds: they differ when the avatar catalog retired that design (it is drawn as its replacement). ?rev=N serves an earlier revision from the home's biography. identity.change is why that revision was written: {cause, written_by, at} from its biography row (cause: recorded_default, chosen; null when the home has no row for it). A home without a record yet gets its recorded default here (unless it is closed for maintenance: 409).
    PUT /api/gateway/entities/{name}/identity An admin or its creator: {avatar: {style, color}, voice: {provider, model, voice, speed?, quality_preset?}}, the whole identity. Refused in this order, for every role: the home is closed for maintenance (409); the design is not one this gateway's avatar catalog knows, active or retired, or cannot be drawn on the Watch (400, the ready designs listed); the voice is not one the caller's voice picker lists (GET /voice/voices?provider= as the caller; 400: "Orion can't speak with zz: it isn't a kokoro voice Orion can use. An entity speaks with this gateway's shared voices and its creator's own voices; another person's own voice stays theirs until an administrator shares it with everyone. Choose one of: …"); its model is not downloaded (409, error.download: "Orion's voice needs the kokoro model kokoro-big (330 MB), which is not downloaded on this computer yet. Download it (the Models page, or: …), then save the identity again."). Never cleared. Each change is rev + 1, recorded in the home's biography and as an identity_changed host marker.
    GET/PUT /api/gateway/entities/{name}/voice Its voice: {provider, model, voice} or {"clear": true}; unset, it speaks with the gateway's default voice (effective). PUT: an admin or its creator (the creator: a voice the caller's picker lists, else 403 not_offered). On a home with an identity record: served from the record (source: identity, never the gateway default in its place), a PUT changes the record's voice through the identity's checks, and clear is refused (409).
    GET/PUT /api/gateway/entities/{name}/appearance How apps draw it (the colour and shape of its orb): {color: "#rrggbb", shape: planet\|kitty\|face\|wave}, the whole look replaced, or {"clear": true}; unset, apps use their own look. Also accepted at creation (appearance on POST /entities) and returned on each row of the list. On a home with an identity record: the record's colour and the shape its design draws (source: identity). The shape designs are retired, so a shape writes the ready design the avatar catalog draws in its place: wave writes watch-wave (read back as wave), kitty and face write watch-halo (read back as planet); a PUT changes the record's look (what is not given keeps its value; the voice is kept), clear is refused (409), and a record with no voice yet refuses a look change with its sentence.

    The digital identity. Every entity has one record in its home, identity.json (AbstractRuntime's format): an avatar design from the abstractavatar catalog, its colour, and its voice. A design the catalog retired is never refused nor drawn blank: it resolves to its replacement (style, the stored id in style_requested). The designs the gateway lists and the looks a legacy shape writes are the catalog's ready designs; experimental designs stay reachable by id. An entity born now gets its identity at birth: the one POST /entities names in identity (checked before anything is created), else the recorded default (a design and colour computed from its id, the gateway's default voice as a value, or no voice when the gateway has none); a birth appearance becomes the default's look (a chosen look needs a voice: refused before creation when the gateway has no default voice). Each existing home without a record gets the recorded default once when the gateway starts (a home closed for maintenance is skipped and logged, a record is never overwritten), else at its first GET /identity. A later change of the gateway's default voice never changes a recorded identity. The entity speaks with the record's voice only: its TTS lanes answer voice_source: identity, identity_ref and the X-Identity-Ref header (entity:orion#3), and a record with no voice refuses with "Orion has no voice yet: choose one in its Identity settings or set the Gateway default voice". The reference also rides each visit (_runtime.identity_ref, beside the signed stamp, and on the open response), each meet leg, relay row and status row, each public update row of a visit, and the visit's state (GET /visit/{run_id}/state, top-level identity_ref); a home without a record carries none. The list rows carry identity (the record with its watch_code, or null). Visits, meet legs and summons record who started them (_meta.origin: kind person, actor the same person:<user> as the participants).

    Whose voices an entity may speak with. The voice checks (identity, the legacy voice door, the identity at birth, a conversation's identity) list the voices exactly as the caller's voice picker does: GET /voice/voices?provider= as the caller, in their runtime plane. On a gateway with user accounts that is the shared library (the built-in voices and the ones an administrator made or shared) plus the voices of the account whose plane holds the entity: its creator's own voices, cloned or designed (an administrator acting on someone's entity is served by that plane). An entity lives and speaks in its creator's plane (every route that makes it speak runs there), so a creator's own voice is heard by everyone who meets it; if the creator deletes that voice, the entity cannot speak with it any more until another voice is chosen. Another person's own voice is not in that plane and is refused with that sentence; an administrator can share it with everyone first (POST /api/gateway/voice/clones/{voice_id}/deploy). A conversation's identity speaks with the shared voices and your own.

    An entity without its own mind thinks with the gateway's text route (the console's text default, with its endpoint and reasoning); a request may still name a provider and model for one visit. There is no environment variable for any of this. The console sets both in Manage → Mind & voice, the Entity app in Settings → mind / voice.

    The cognition profile. Beside its mind, an entity has a cognition profile (cognition.yaml in its home, AbstractRuntime's format):

    Setting Default Range
    capabilities.summaries (summaries and memory details), capabilities.understanding (understanding and dreams), capabilities.extraction the mind {"inherit": "mind"} or {provider, model, thinking?, max_input_tokens?}; thinking one of none, minimal, low, medium, high, xhigh, auto, on, off; max_input_tokens 4096 to 140000 (140000 when not given)
    recall.shelf_size: memories retrieved per turn, in visits and in its own time 50 whole number 1 to 400
    rebuild.sensitivity: how easily a new memory or a surprise makes it revisit what it already understood 0.5 number 0 to 1
    rebuild.cap_per_turn: memory rebuilds a turn may run at most (0 = only while it rests) 3 whole number 0 to 10
    lookback.context: what the look-back at the end of a tick of its own time sees day day: the whole day so far (about constant new tokens per look-back with a prefix cache); tick: this tick's exchange plus a recap of the day's 12 latest earlier moments
    sleep.after_hours, sleep.after_events: when an idle entity goes to sleep on its own 24, 500 whole numbers; hours 1 to 720, events 1 or more. Counted since its last completed sleep: hours, or new memories formed

    Talking always uses the mind. A visit (chat/open), a durable visit, a summon and the start of its own time use recall.shelf_size when the request names no shelf_size; a request's own value still wins. A running own-time day reads the width when it starts: a change applies from its next start, including a restart after a crash.

    Every memory the entity forms gets its title and summary from the capabilities.summaries model at the moment it forms, in a visit, a durable visit and its own time alike. When that model cannot answer, the memory forms without them and is completed later: at the next step of its own time, when a visit closes, or during its sleep. A summaries model on a provider connection works in its own time too.

    Progressive disclosure: inspect shows diary gists only. The verbatim prose stays in the book and is fetched by the entity itself during a session (DIARY_READ), never bulk-exported by inspection.

    The task inbox (tasks left with an entity)¶

    Tasks are durable facts in the home — append-only events in <home>/task_inbox.jsonl, folded at read (state is never rewritten in place; two writer processes exist — the door and the own-time loop — so every write is one flock-guarded appended line):

    Method Path What it does
    GET /api/gateway/entities/{name}/tasks The folded inbox: tasks with current status (pending\|taken\|done\|parked), chronological. exists: false when no inbox was ever created.
    POST /api/gateway/entities/{name}/tasks Leave a task (admin): {title, brief?, workflow?, backlog_ref?}. origin/by are STAMPED from the authenticated principal — the body carries no origin field to forge. Marker-first (task_inbox_changed); a marker failure refuses the write.
    POST /api/gateway/entities/{name}/tasks/{task_id}/status Advance a task (admin): {status, note?}. Validated before the marker; unknown tasks 404.

    A visit can leave tasks at close: POST .../visit/{run_id}/close accepts tasks: [{title, brief?, …}], recorded with origin visit:<run_id> only after the close COMPLETED (recording failures surface as a labeled warning in the response — the finished close is never misreported as a 5xx).

    Skills (what an entity is taught)¶

    Beyond the always-verbatim capability map, an entity's skills are an operator SELECTION in the home (<home>/skills.yaml: [{name, phases?}], phases from the ruled four, absent = selected everywhere), resolved server-side against the abstractskill shelf through the same trust gate as every other lane — default-requested, never trust-bypassed:

    Method Path What it does
    GET /api/gateway/entities/{name}/skills One resolved truth for every UI: the stored selection, roster rows (name, description, trust_level, requires_review, tree_hash, source) with labeled verdicts for anything unresolvable, and the capability-matrix payload (a global selection renders all four phases with identical cells).
    PUT /api/gateway/entities/{name}/skills Replace the selection (an admin or its creator). Marker-first (skills_selection_changed, old/new names+phases — never skill bodies); the response is the resolved view so a typo or blocked skill is visible the moment it is written.

    POST /api/gateway/entities accepts the same selection at birth (skills: [{name, phases?}]) so a new entity carries teaching from day one. Selections pin by NAME and resolve to the current shelf state at read/summon time — a shelf re-pin reaches homes on their next resolution, never by bulk push. Delivery into entity prompts (progressive disclosure: names ride the base, bodies activate on demand) waits on the runtime's composition-slot election; the selection file rests in the home until then.

    The entity roster (GET /entities) carries pending_tasks render-when-present: the field exists only for homes that have an inbox — an entity never handed a task shows no field, not a zero. The file schema is the cross-package contract for the runtime's day-open reader (the R-C loop half): event lines {"event": "added"|"status", "task_id", …} — see abstractgateway/entity_tasks.py for the authoritative shapes. The inbox records facts; whether a task opens the work phase is decided by the entity's loop.

    Drive ratios (cognition health)¶

    GET /entities/{name}/cognition carries a drives block — memory's cognition_health() fold over the home's full ladder: questions open/resolved, problems open/repaired, interests open/explored, each with a ratio that is null when the category is empty (a life with no questions has no ratio, never a fabricated 100%). Ratios are data — never-100% is the design (an entity with nothing open has no pull forward), so consoles render an amber cue at saturation, not a success state. Render-when-present: the key is absent (with a labeled #FALLBACK warning) when the engine predates the read or the read fails.

    The roster (GET /entities) carries the same drives block for warm homes only — homes already open in this gateway process. The roster is deliberately file-cheap and never opens a store; a cold home shows no field (absent ≠ zero), and /cognition always serves the block (and warms the home). The gateway console renders the two ratio bars in the entity Overview panel from the same /cognition read.

    Live conversation during a visit¶

    Open POST /api/gateway/entities/{name}/visit/open with a stable session_id and optional conversation: true (a strict JSON boolean) to enable public updates and conversational questions. The mode is fixed before the first tick; rejoining an existing managed session with a conflicting mode is refused (422). Existing tool policy remains separate; ask_user is an interaction primitive in this mode even when external tools are off.

    The open never fails because the entity is busy: when its own time is running, the request waits, with no time limit, until the entity has finished the step in progress (it starts no new tool call once a visitor is at the door), then the visit opens.

    Read GET /api/gateway/entities/{name}/visit/{run_id}/state. In conversational mode it adds:

    • public_updates: up to 64 explicit, safe actor updates with id, text, run_id, session_id, iteration, source_call_ids and update_kind ("finding" or "progress", as typed by the actor).
    • public_messages: up to 64 accepted human corrections with role: "user", kind: "guidance", id, text, run_id, session_id, speaker and guidance_status: "accepted".
    • public_questions: up to 64 canonical ASK_USER interaction messages: assistant question, user answer, system question_outcome for expiry, and user retained_reply with reply_status: "retained" and its reason. Question/answer rows retain their actual wait_key; question_id comes from the original wait when available. Expiry retains question.outcome: "expired"; retained replies keep the original question id. The server selects only known ASK_USER sources and trusted host outcomes, screens diary/thinking fences, and never serves generic home messages or reasoning as question history.
    • public_updates_omitted, public_messages_omitted, public_questions_omitted, conversation_runs_omitted: explicit counts when this bounded view omits entries or descendants; the full ledger remains. Question omissions include rows withheld by privacy-fence screening. Clients show a history omission notice when any count is positive.
    • pending_question: null or the actual question wait, including its child run_id when applicable, wait_key, prompt, choices, allow_free_text, until and details.question. When present it is also the pending_wait. All pending waits carry their actual run_id.

    A permission pending_wait.details.public_action, when present, carries the actor’s explicit public explanation (text, update_id, run_id, iteration, call_ids). It is bound to the exact pending batch and narrowed when the session tool policy withholds actions. It grants no permission and does not prove execution. A missing explanation must not be reconstructed from private thoughts or another update.

    This is a participant-facing projection over the owned visit and verified descendants, bounded to 32 runs. Clients must not read the entity home's raw ledger or diary to render it. Explicit public events still undergo server-side diary/thinking-fence screening; an event marker alone does not make private content public. All three public message arrays retain canonical order: [timestamp, run_id, ledger_seq] and published_at (the same timestamp, from the record's end or start time). They are chronologically ordered before the 64-entry cap. Clients merge the arrays by this order; grouping all human input before actor updates would change the history.

    While the entity is working in its current turn, send POST .../visit/{run_id}/guidance with {text: "quoted context and correction", display_text: "the person's original words"}. display_text is optional; this authenticated human visit route uses text when it is absent. Display words must be nonblank and at most 65,536 characters. The server derives the participant identity; clients cannot choose it. The response {accepted: true, seq, run_id} means durably queued, not adopted. Idle, paused or currently waiting visits refuse live guidance (409); send the next turn or answer the actual wait instead. Accepted corrections are recalled and attributed before the next reasoning boundary, with no additional model call for empty queues. Old-turn corrections remain retained instead of silently becoming instructions for a new turn.

    Answer a conversational question through POST .../visit/{run_id}/answer with {wait_key: "question:<id>", response: "the person's words", target_run_id?: "<actual child>"}. An omitted target selects the actual pending question; an explicit target must be a verified descendant in the same owned visit. Empty text, extra approval fields and tool-approval waits are refused; this route does not approve tools. It returns {accepted, run_id, target_run_id} with the refreshed safe conversation projection. Paused visits refuse answering without continuation. Late recognized replies are retained under Runtime's question contract and cannot answer a newer question. Essential questions have no deadline; timed clarifications apply only their predeclared safe fallback. See api.md.

    Attach files to a turn: POST .../visit/{run_id}/turn takes attachments: [{"path": "..."}] beside text and speaker. path is workspace-relative — the string POST .../workspace/file returned when the file was placed (mounts/<name>/… is allowed). The gateway resolves each path through the entity's own workspace rules and records {path, bytes, sha256, content_type} on the turn (the content type comes from the bytes for PNG, JPEG, GIF and WEBP, else from the name). Refusals, before any state moves, each with a code: an unknown path is 404 (attachment_not_found), a path outside the workspace or an unknown or refused mount 403 (attachment_outside_workspace, one fixed sentence that never names the mounts), a directory 400 (attachment_is_directory), an empty path 400 (attachment_path_required), a path the host cannot read — an embedded NUL, a name too long, a symlink loop — 400 (attachment_unreadable), a file over the 20 MB workspace cap or a turn whose files total more than 64 MB 413 (attachment_too_large, the total in the detail); at most 64 files per turn (422 beyond). Images are attached to the entity's model call with the message, on every model call of that turn (whether the mind can see them is the provider's business: a text-only model is given nothing); other files are recorded and named in the message, and the entity reads them with read_file. The message the entity sees gains one line per file, for example (attached: shared/x.png — a PNG image, 1,204,113 bytes; attached to this message as an image; read_file re-opens it); the visitor's words are not rewritten and nothing is parsed from them. GET .../visit/{run_id}/transcript carries the records on the user turn as attachments. When the entity itself reads an image with read_file, the result is a short #IMAGE label and the image is attached to its next model call; GET .../visit/{run_id}/ledger serves such media paths workspace-relative.

    Tool approvals keep their existing /decision route and exact pending key; they never time out into approval. A managed visit's authenticated owner is checked before these routes; wrong-owner requests do not disclose it. Generic run steering remains refused for these driver-owned visits. A Flow summoned work session is a separate ordinary Gateway run: it uses /runs/{root}/view and standard commands, not the driver visit routes above.

    Summoning¶

    Summoning opens a work session as the entity:

    1. The gateway renders the identity header ("summon prelude": who you are, your values in ordinal precedence, your recent diary lines, your standing feelings). This is a pure read.
    2. A refused prelude aborts the summon. If the budget cannot fit the identity core, the request fails (409) with the reason verbatim — "a truncated core is a different person". There is no fallback to a truncated header.
    3. The run starts with the reserved-seats posture: identity is always present in the working set (self_fraction > 0), and presence never counts as use — the lifetime counters keep measuring lived experience.
    4. The prelude leads the run's system prompt; the work brief is the prompt.
    curl -X POST http://localhost:8080/api/gateway/entities/orion/summon \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"prompt": "Review the backup strategy for the home lab."}'

    The response carries the run_id, the session id, and the rendered prelude. The run behaves like any other gateway run (ledger stream, waits, cancel).

    Mentioning an entity from any chat¶

    Any chat window (TUI, web, an app) can bring an entity into its conversation with @name. The client picks the entity from GET /entities (a structured choice: the gateway never looks for @ in text) and sends the message:

    curl -X POST http://localhost:8080/api/gateway/sessions/$SESSION_ID/mentions \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"entity": "orion", "text": "@orion does the backup plan hold?", "mention_index": 0, "mention_id": "<optional>", "repeat_of": "<the agent turn run id, optional>"}'

    mention_id (optional) is your own id for this mention. Sending it again (a double submit, a retry after a lost response) returns the first answer; the entity is never asked twice.

    What happens:

    1. You are the visitor. The speaker is the signed-in person, never a name the client sends.
    2. One life, one visit. The entity's live visit is reused only when this door opened it, in this conversation, for you. With none, a visit is opened for this conversation; it closes on its own (with the usual reflection) after 5 minutes without a mention. If that close lands just as you mention again, a fresh visit opens.
    3. The entity reads the conversation and lives it at home. Your text is a turn of that visit, preceded by the conversation's recent turns quoted with who said them (Alice: ..., Agent (Basic Agent): ..., Orion (entity): ...; built from each turn's author, never from the text): the newest whole turns, at most 12 turns and 8,000 tokens, whichever comes first. A turn too long to quote on its own is left out, with a note, and the others are still quoted. Attachments are named ((attached: contract.pdf)). A reused visit is sent only the turns newer than its last mention: it already holds the rest. The answer's context states what was quoted and what was left out (skipped_oversize included). The entity's own ledger, memory and artifacts hold the episode, quote included, exactly like a visit from the Entity app.
    4. The answer is a turn of your conversation. The reply is recorded in the session (a completed run, workflow entity-mention), so session history, GET /runs/{id}, the replay view and every client show it, and the conversation's agent sees it in the next turn's history as orion (entity): ..., never as its own words.

    Several mentions in one message are separate requests, in order (mention_index 0, 1, 2...), each its own turn.

    The same words, once. When the message also started the conversation's agent turn, send that turn's run id as repeat_of (it must be your own turn of this conversation, with the same words): the mention turn keeps the words as its prompt (history and replay stay whole user/answer pairs, so the agent still hears the entity's reply) and is marked repeat_of on every surface, so a client shows the person's words once and folds the entity's answer under them. A repeat_of that is not a turn of this conversation answers 422 repeat_of_unknown. The mention turn is dated when your words arrived (created_at) and when the reply came (updated_at), so the answer always sorts after the question.

    In a visit. When the conversation is the live visit of the entity you are visiting (an Entity-app visit with Leo, session_id = the one visit/open returned), the mentioned entity reads THAT visit's exchange (your words and Leo's answers) as the conversation, and its reply is also a turn of THAT visit, spoken by the mentioned entity: the door adds entity:orion to the visit's signed participants, then sends Orion (entity): <reply> as a visit turn with that speaker. Leo hears it and answers it like any visitor's words; his home's ledger and memory keep it. The answer lists these under mirrors ([{entity_id, run_id, turn_id, reply}]; reply is Leo's answer to THIS turn, or null with an error sentence when he could not answer it. When his model call fails on that turn, reply is "This turn could not be answered: …" with the cause in turn_error, and his visit stays open. [] in a plain chat: two entities mentioned in one chat never mirror into each other).

    The answer (200):

    {"run_id": "<the session turn>", "turn_id": "<the turn in the entity's home>",
 "author": {"kind": "entity", "name": "Orion", "entity_id": "entity:orion",
            "identity_ref": "entity:orion#3", "avatar": {"style": "watch-halo", "color": "#336699"}},
 "session_id": "...", "mention_index": 0, "repeat_of": null,
 "context": {"turns": 3, "tokens": 412, "max_turns": 12, "max_tokens": 8000, "dropped_turns": 0,
             "older_turns_not_read": false},
 "reply": "...",
 "notices": [],
 "visit": {"run_id": "<the visit run in the home>", "turn_id": "...", "visit_id": "visit-...",
           "entity_id": "entity:orion", "reused": false},
 "mirrors": []}

    Errors ({detail, code, session_id} plus the X-Gateway-Error-Code header; session_id is always your own conversation):

    Status code When
    404 entity_not_found No such entity, or one this account may not see (a member mentions only the entities they created; a hidden entity answers like a missing one)
    409 in_another_conversation The entity is in another conversation. Only one of your own conversations is ever named (session_id); another account's never is. It is free again when that conversation ends or after 5 idle minutes
    409 stopped_use_resume The entity is stopped (the kill switch)
    422 repeat_of_unknown repeat_of is not your own turn of this conversation with the same words
    503 entity_cannot_answer "Orion cannot answer right now. Try again in a moment.": its mind cannot be resolved (no model chosen), or the turn gave no reply (the cause is in the gateway log, never in the sentence)

    Who speaks, on every turn. Session history (GET /sessions/{id}/history/bloc rows and each bundle's run), GET /runs/{id}, the replay view's user and assistant messages, and the run.started/run.finished events and every live reply frame (llm.delta, llm.delta_end on /runs/{id}/ledger/stream) carry author (the answer) and, where a prompt is shown, prompt_author: {kind: "entity"|"agent"|"person", name, entity_id, identity_ref, avatar: {style, color}|null}, every key present. An agent's turn is named by its workflow (workflow_selection.name, never a model name); a person's by the account's display name; a summon's answer is the entity's.

    Who answers: mentions on the agent's turn and on a summon. The same chips also go on POST /runs/start as mentions (names or slugs, never parsed from the text), with the reserved chip agent when the message is also for the conversation's own agent (no entity can be named agent). A missing, hidden or invalid name answers 404 entity_not_found. Without agent, the agent's run is not started: the person's turn is recorded on the session, the answer says agent: "not_addressed" with that turn's turn_id (send it as repeat_of here; it is also the turn's run_id), and the turn carries agent_addressed: false wherever a reload reads it (GET /runs, the history bloc, the replay view). With agent, the agent's run starts (agent: "started") and the agent reads, as the last instruction before your words: "The mentioned entities (Orion) answer this message themselves. Unless the user addressed you directly, reply with an empty message." Staying silent is still the model's judgment: a model may answer anyway. POST /entities/{name}/summon follows the same rule: the summoned entity answers when the chips name it, name agent or name nobody; chips that name only other entities start no summon run.

    What a turn formed: notices. A turn's answer carries what the entity formed or staged during it, unchanged: [{kind, record_id, title, text?, staged?, visibility?}], and the reply it serves carries no bracket markers (the stored words keep them). A mention answers notices and records them on its session turn, so GET /runs rows and the session history bloc carry them too ([] for a turn that formed nothing); a mirrored turn's row carries the visited entity's. The hosted chat turn and the visit door's turn answer reply_notices beside the reply (on the visit door, notices stays the operator's log lines). The visit close answers notices: each election the visit's turns staged that the close formed, with the formed record's graph id.

    His topics (memory's communities)¶

    An entity's memories group into topics while it sleeps. Memory forms them (AbstractMemory's communities_pass, run by the runtime's night after the metadata repair) and keeps each topic as a community record with an authored title and summary; the gateway serves what memory formed and computes nothing on a request.

    flowchart LR
  night["his sleep: repair, then topics"] --> version["memory: a new version of his topics"]
  version --> stream["replay stream: one communities_changed marker"]
  stream --> app["Entity app re-reads /communities"]
  version --> route["GET /communities and GET /graph"]
    • Where they form: every sleep the gateway runs (the operator's sleep, the idle sweep's) runs the runtime's night (build_consolidator): memory's sleep pass, the repair of titles and summaries, then the topics (what has no vector is embedded first with the home's own embedder), then the night voice. The own-time loop runs the same night. A Stop ends it at the next step; nothing is written after it.
    • GET /entities/{name}/communities: memory's payload version 2, unchanged: {version, version_seq, first_sleep_pending, algorithm, communities: [{id, key, title, summary, pending, verdict, size, kinds, members: [{id, via}], provisional_ids, cohesion, layout: {xy, radius, seats}, centroid_stale, facts}], links: [{a, b, weight}]}. key is stable across versions (id is the version's record). A topic whose title is still being written says so in pending (title null), never a keyword label. Before his first sleep: first_sleep_pending: true and no topics (the app says his topics form at his first sleep). Cached per home and journal position, so a memory formed since the version shows in provisional_ids.
    • GET /entities/{name}/self-brief: his self-knowledge brief, what he knows about at a glance: the runtime writes it at the end of a sleep's topics stage into <home>/self_brief.md (a projection, never a memory) and places it in his prompt prefix (AbstractRuntime 0.19.1, identity/self_brief.py). Served as {text, written_at, version, tokens} (version = the communities version_seq it describes). 404 no_brief before the first sleep that wrote one; 500 for a file that is not a brief. The Entity app shows it on his Identity page (the Files view lists only his workspace).
    • GET /entities/{name}/graph: the whole graph the app draws, in one read: {version, journal_seq, communities_version, communities, nodes, edges}. Each node is an open formed record (community records never are) with the latest display block of its binding (exactly as the replay serves it), its topic key, via and seat from the communities read; edges are the formation edges between nodes. Folded once per process and home, then only the stream's tail since journal_seq; the app tails the live stream from there.
    • The live marker: when a new version's records pass through the replay stream, the gateway records one host marker {kind: "communities_changed", version_seq} per version; the app re-reads /communities on it. A community record's binding draws its revision chain only, never an edge per member.
    • One memory's topic: the record read (GET .../records/{graph_id}/verbatim) and the card's record briefs carry community: {key, title, pending, provisional, via} or null, so a hover card or the Detail tab can say which topic the memory is in.
    • The entity's own view: the topics tool (tier 1, read-only) reads the same communities in visits.
    • Sleeping when fragmented: besides sleep.after_hours and sleep.after_events, an idle entity sleeps once more than sleep.after_fragmented_share (cognition profile, default 0.15) of its memories are not yet whole (placed provisionally, without a vector, or with a title or summary still being written), if something formed since its last sleep; the sleep's reason says the share.

    The deposit gate (actor by channel, never by payload)¶

    Every write to an entity's home passes a door that derives the actor from the channel the request arrived on — never from request payloads:

    • workplace — summoned work sessions. Routine feelings only (small amplitudes); no identity writes; no belief retraction; no diary forgery (the diary is written through the entity's own elected act, DIARY_WRITE, whose author is bound at construction).
    • entity-reflection — runs the home itself spawns (the future heartbeat / reflection loop). This is where identity evolves.
    • operator — the authenticated admin surface (CLI, admin HTTP).

    Mechanics: the summon endpoint signs a stamp (HMAC, per-data-root secret) over the entity, channel, session, and run id; the routing layer verifies it before any home opens. A payload claiming a privileged actor fails loudly. The stamp authenticates "minted by this gateway" — remote workplace authentication is the deferred key/signature work. This is the AI-fingerprints direction applied at the door: identity verified at the boundary, never self-claimed.

    The gate also enforces:

    • The privacy boundary: a session's recall ladder may only contain the entity's own scopes plus that session's scope — never another user's.
    • The summon posture and the identity floor: a recall budget that omits self_fraction gets the posture default; an explicit self_fraction <= 0 is rejected ("identity is always present for a summoned entity"). Below the hard floor (5% and at least one reserved seat) nobody goes; reducing identity presence below the default — hyperfocus, a conscious and risky tradeoff — is the entity's own act (entity-reflection channel only, reversible by construction: per-session, never persisted). A stripped entity may act out of character; workplaces cannot request it.
    • Anchors: journal time-travel anchors beyond this entity's own journal are rejected.
    • Verified participants: who is present in the session is stamped by the door from the authenticated principal and flows into recall and formation (the situation contract) — payload claims are dropped.

    Observing a life (the replay stream)¶

    The replay endpoints serve the memory engine's frozen stream (one envelope shape; the journal is the stream) merged with gateway host markers — moments that are deliberately invisible to the entity's own journal because nothing happened memory-side (a prelude render is a pure read): summons, refused preludes. Markers are gateway bookkeeping (like run ledgers), stored outside the home directory, and take fractional sequence positions so they interleave without ever colliding with the journal.

    Privacy: the engine redacts diary display blocks at the source ({"redacted": "diary"}). These HTTP endpoints serve the OPERATOR audience, so the serving end resolves that marker into the entry's gist — the entity's one-sentence summary, or the first ~120 characters when no explicit gist exists (_operator_diary_display). So the operator sees the diary's topology (the entity wrote something, it connects to something) and a gist of what it was about — never the full verbatim prose, which stays in the book and is fetched one entry at a time through the operator diary door (GET .../diary/{entry_id}, a marker-first recorded read). The redaction marker itself is never served raw.

    A step's tools and files (step_tools)¶

    Each finished step that ran at least one tool (a visit turn, a tick of own time or work) is followed on the stream by one host marker, so a ledger row can say how busy the step was with no further read:

    {"kind": "step_tools", "session_id": null, "run_id": "…", "turn_id": "t-0002",
 "tools": ["web_search", "read_file", "read_file", "write_file"],
 "tool_count": 4, "files_read": 2, "files_written": 1}
    • tools are the calls that ran, in call order (a call the tool grant or the turn's budget refused did not run); tool_count counts them.
    • files_read counts read_file and skim_files; files_written counts write_file and edit_file. Listing, searching and execute_command count as tools only. One table decides this (entity_step_tools.py) until AbstractCore declares a file effect on each tool.
    • The marker comes after the step's own rows: join it to them on run_id and turn_id. It is on the bounded replay and on the live tail. A step that ran no tool has no marker, and the marker is never a moment of the life (the entity card's moments leave it out).
    • A visit step's calls are noted by the gateway's tool handler and the marker is written when the step answers (or fails with what it already did). Own time runs in the runtime's loop process: its step's episode keeps the names of the tools it ran, and the gateway writes the marker when a stream read reaches that episode. Those steps are counted from the home's first stream read on this gateway version; earlier steps get no marker. The sleep's passes run no tool, so a sleep has no marker.

    Reading a record's verbatim¶

    GET /api/gateway/entities/{name}/records/{graph_id}/verbatim serves the full stored text behind a memory record (the digest is prompt currency; the verbatim is the lossless original). Three shapes:

    • Lived records (episodes, notes): served from the home's artifact store, lossless.
    • Identity records (values/purposes/traits): their verbatim IS the attested spark document — the endpoint serves the spark text itself.
    • Born-digest records (interests, dreams, world-model cards, lessons formed without a verbatim): born as words — their digest is their complete text, never a compression. Served as-is with born_digest: true ("the words you see are all the words there are").
    • Summaries without a verbatim (older session reflections, the mechanical floor): served with their digest as the text, born_digest: false and summarizes (the graph ids of the records the summary covers). Any other record without a verbatim is an honest 404.
    • Diary projections: served to the operator from the book. The read is marker-first: a diary_read host marker (entry id, kind, visibility) lands in the entity's replay stream before the words return, so the disclosure is recorded in the entity's biography. Private entries are included. Born-digest diary kinds (interest/dream) serve their digest as the verbatim.

    What an entity retrieved: tool-result artifacts¶

    Every tool result during an entity's activity — a visit's web search, a fetched page, a file it read, an image it looked at, a command's output — rests whole in the entity's home as an artifact (the runtime's keep_tool_result_artifact; the result text the entity read ends with [artifact: <id>], the visit ledger's tool_calls rows and the transcript's tool_details carry artifact_id). Book-adjacent tools (diary_read, diary_list, search_memory) store nothing: their content is the home's own book and graph. Three read-only routes serve them, from the home's own store, with no file path in any answer:

    Method Path What it does
    GET /api/gateway/entities/{name}/artifacts?run_id=&tool=&turn_id=&limit=&cursor= Metadata rows, newest first, bounded (limit 1–500, default 50; next_cursor for the next page). Each row: artifact_id, content_type, size_bytes, created_at, run_id, tags (kind: tool_result, tool, lane, entity_id, turn_id or tick_id, session_id) and metadata (the tool, its arguments, shown_is_view when the entity saw a bounded view of these bytes, bytes, failed).
    GET /api/gateway/entities/{name}/artifacts/{artifact_id}/meta One row; 404 when no such artifact.
    GET /api/gateway/entities/{name}/artifacts/{artifact_id} The bytes with their stored content type (a page as text, an image as the image); X-Artifact-Id names it; 404 when no such artifact.

    A record's stored understanding (who wrote these words)¶

    AbstractMemory rewrites a record's words (its digest) in place and keeps every earlier reading as a version. The gateway serves what memory stores, under memory's own names, so an app can say "Summary by Leo's mind (qwen3.8-27b), 7 Nov" or "Extract (mechanical)" without guessing from the text. Every block carries all of these keys; a value the store does not hold for the record is null, never a missing key:

    Field Meaning
    digest The words of the reading
    digest_method How they were made (mechanical-v2, mechanical-card-v2, authored-v1, ...)
    digest_version Which reading (0 = the original)
    version_count How many readings the record has (1 = never rewritten)
    authored_by {kind, id}: mechanical (id = the digest method), entity-mind (id = the entity, for the words it wrote itself), capability-model, operator (a spark record: spark-v<N>), or unrecorded when nothing says who wrote them
    reader {provider, model, thinking} of the model that wrote the words (null for mechanical and operator text)
    understood_at When this reading was formed
    cause Why it was written: formation, backfill, ripple, evidence, operator, revert
    target, target_type, card_revision, source_count World-model cards: who or what the card is about, its revision, how many records it was built from
    narrated, narration_version Dreams: whether a narration is stored beside the summary
    replaced_by A superseded record: the graph ids of the records that replaced it

    Where the app reads them:

    • The record read (GET .../records/{graph_id}/verbatim): every non-diary answer carries the fields of the record's current reading and versions, memory's list of every reading, oldest first (each with version, text, digest_method, author, reader, cause as {cause, ...}, understood_at, seq and current; empty when the record was never rewritten). Private non-diary records carry the same understanding fields (digest, digest_method, versions, authored_by, ...) as the public ones.
    • Recall snapshots in the replay stream (family: "snapshot", with enrich=true): display.recalled holds one block per recalled record (record_id as the snapshot lists it, graph_id, kind, then the fields). The words and their provenance (digest, digest_method, digest_version, authored_by, reader, understood_at, cause) are the reading that entered that context, so digest equals the snapshot's own row; version_count, replaced_by and the card and dream fields describe the record now. The payload (the journal record) is unchanged.
    • The card (GET .../card): each record brief in discoveries.interests, lessons.lessons and key_moments.moments carries the fields of the current reading (its statement is the same words as digest).

    Diary records get none of the gateway's additions: their record read is the book entry as before (a recorded diary_read) and recall snapshots do not list them in display.recalled. On the card, memory's own diary briefs (questions, problems, book lessons) carry who wrote the entry, when and why (authored_by, understood_at, cause, ...), never more of its words than before. The reads deposit nothing in the entity's memory.

    The operator diary door (reads are visible events)¶

    GET /api/gateway/entities/{name}/diary/{entry_id}?reason=... serves a book entry — private included — to the operator channel. The book already lives unencrypted on the operator's machine; this door makes each read recorded rather than silent. reason is optional (default "operator review"; the identity, the act and the timestamp are the audit record), and every disclosure lands a diary_read host marker (entry id + reason) in the entity's replay stream before the words return — the entity's biography shows who read it and why. Failed lookups disclose nothing and are not marked. Both full-content doors (this one and the record-verbatim endpoint above) serve the operator; the boundary that stays closed is the effect layer (a workplace channel cannot read the book), not the operator's HTTP surface.

    What can never be relaxed¶

    • Never-purge and only-entity-writes are structural (absent code paths and construction-bound authorship), not policy checks.
    • A refused prelude aborts the summon.
    • Actor strings are made true at the door; everything downstream trusts them.
