    Engine installation, per engine and per OS¶

    What POST /api/gateway/engines/{id}/install (and abstractgateway engines install) runs on each operating system, what it requires, where the files go and how the GPU backend is chosen. The rules are ADR 0003 (engine installation contract): an engine is installed once per computer, under the gateway's service account (the account the gateway process runs as), and shared by every user of the gateway; never with root when the vendor offers a non-root path; prebuilt binaries and wheels only, never a source build or a compiler; the same states and sentences on every OS; an update is atomic (the old version stays if the new one fails). Audited 2026-10-29 against src/abstractgateway/engines_install.py and AbstractCore's config/engines.py.

    <native> is llama-cpp-python, torch, torchvision, torchaudio, vllm, mlx, mlx-lm, mlx-metal (engines_install.PREBUILT_ONLY). Every Python install keeps the gateway's own abstract* packages at the versions it runs, and every Python engine update is atomic: the packages it changed are reinstalled at their previous versions when the install or the load check fails.

    Known gaps (2026-10-29)¶

    • Windows Ollama and LM Studio run AbstractCore's vendor commands through the generic job ("Running the vendor installer for …"): the states are the shared ones, but the progress and failure sentences are less specific than on macOS and Linux, and the vendor installers handle their own updates (atomicity is the vendor's). Not run on a real Windows desktop yet.
    • LM Studio on Linux is the vendor's script: its update is the vendor's (not swapped by the gateway), and libatomic1 stays an administrator step on minimal images.
    • Ollama on Linux needs zstd, a system tool; the AbstractFramework server installer adds it.
